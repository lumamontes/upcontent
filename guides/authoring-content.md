Good documentation is task-oriented, explicit about its audience, and easy to scan. This guide describes the conventions used in a clear technical documentation site.

## Start with the reader's task

Prefer a page title that completes the sentence "I want to...":

- Good: `Configure a consumer repository`
- Weak: `Configuration`

Open with one or two sentences that explain the outcome. Put prerequisites before the first action. Keep each section focused on one decision or step.

## Use frontmatter deliberately

Every page can declare metadata at the top of the file:

```md
---
title: Configure a consumer repository
sidebar:
  order: 2
---
```

The title becomes the page heading and the default sidebar label. The description is used for page metadata and search context. Use `sidebar.order` only when ordering carries meaning; otherwise let the portal sort pages consistently.

## Structure headings for scanning

The page title is the top-level heading generated by Starlight. Start body sections at `##`:

```md
## Before you begin

## Configure the repository

### Add the portal configuration

### Verify the result
```

Short sections, descriptive headings, and lists help readers find the answer without reading every paragraph.

## Show commands in context

Use a language tag and explain what the reader should observe:

```sh
make build CONTENT_PATH=.
```

Do not show commands without saying where to run them, what they change, or how to verify the result. Use placeholders for values that readers must replace:

```sh
make dev CONTENT_PATH=/path/to/your-consumer-repo
```

## Link to stable concepts

Use normal Markdown links for known pages. Use wiki links when the source repository needs filename-oriented references:

```md
[Validate your site](../guides/validate-your-site/)
[Capability showcase](../showcase/)
```

Wiki links must resolve to a document. The build fails when a target is missing, so a typo cannot silently become published broken navigation.

## Use callouts for decisions

Callouts should contain short, consequential information:

:::tip[Prefer the smallest change]
Start with consumer configuration and CSS tokens before adding implementation code.
:::

:::caution
Static output is public wherever the selected host is public. Repository privacy does not automatically make the published portal private.
:::

Avoid turning every paragraph into a callout. If everything is highlighted, nothing is prioritized.

## Make examples executable

The showcase uses real examples for Mermaid, JSON, YAML, CSV, callouts, and palette switching. Prefer examples that can be built and inspected over decorative snippets that are never exercised.

When an example depends on a file, keep that file in the repository and include the validation command in the surrounding text.

## Content review checklist

Before publishing a page, check:

- The title describes the reader's outcome.
- The first paragraph explains why the page exists.
- Prerequisites appear before actions.
- Headings begin at `##` in the body.
- Commands include their working directory and expected result.
- Links use stable page paths and wiki links resolve.
- Warnings explain a real risk rather than adding visual noise.
- The page was built and inspected at desktop and mobile widths.
